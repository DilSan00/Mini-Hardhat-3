## ⚙️ Механизм Выполнения Модулей (Module Execution)

Выполнение Ignition — это не просто последовательный скрипт, а умный процесс, основанный на графах зависимостей.

### Загрузка и Журналирование (Journaling)

1.  **Загрузка:** Hardhat Ignition читает файл модуля (`.ts/.js`) и использует `buildModule` для создания всех **Future** (планов действий).
2.  **Журнал (`journal.jsonl`):** Ignition использует технику **write-ahead logging**.
    * **До действия:** Записывает в журнал план (конкретный `Future` с его конкретными значениями).
    * **После действия:** Записывает в журнал результат (успех или провал).
    * **Важно:** Журнал нужен для **возобновления** деплоя. Он не хранит сам код модуля, только историю действий.

### Сверка (Reconciliation)

Перед возобновлением деплоя (если есть старый журнал), Hardhat Ignition проверяет, **совместим ли** текущий модуль с предыдущим состоянием.

| Изменение | Совместимо? | Примечание |
| :--- | :--- | :--- |
| **Добавление** новых `Future` | ✅ Да | Всегда можно добавить новые шаги. |
| Изменение `Future` для **того же результата** | ✅ Да | Если `m.contract("Foo", [param])` с `param=5` меняется на `m.contract("Foo", [5])`, это совместимо. |
| **Удаление** невыполненного `Future` | ✅ Да | |
| **Удаление** успешно выполненного `Future` | ✅ Да (с предупреждением) | |
| **Несовместимое изменение** | ❌ Нет | Придётся **сбросить** (`wipe`) или **откатить** изменение. |

### Порядок Выполнения и Пакетирование (Batching)

1.  **Граф Зависимостей:** Ignition строит граф, где каждое `Future` — это узел. Ребра — это зависимости (явные или неявные).
2.  **Пакеты (Batches):** Граф делится на пакеты действий, которые могут выполняться **параллельно**.
    * Пакет 1 включает `Future`, у которых нет невыполненных зависимостей.
    * Следующий пакет выполняется только после **полного завершения** всех `Future` в предыдущем пакете.

### Выполнение Транзакций

1.  **Симуляция:** Каждая транзакция сначала **симулируется** через `eth_call`. Если симуляция падает, выполнение прерывается.
2.  **Подтверждения:** `Future` считается выполненным, только когда его транзакция получает **требуемое количество подтверждений** (`requiredConfirmations`).
3.  **Увеличение Комиссии (Fee Bumping):** Если транзакция "зависает" дольше таймаута, Ignition **автоматически отправляет её повторно** с более высокой комиссией, пока не достигнет лимита попыток.

## 📦 Артефакты Развёртывания (Deployment Artifacts)

Всё, что связано с деплоем, хранится в папке `./ignition/deployments/<DeploymentId>`. Рекомендуется **хранить их в системе контроля версий** (Git).

* **`journal.jsonl`**: Журнал всех операций (для возобновления).
* **`deployed_addresses.json`**: Самый важный файл. **Карта адресов** всех успешно развёрнутых контрактов (`Mod#futureId: "0x..."`).
* **`artifacts/`**: Скомпилированные артефакты контрактов, специфичные для этого деплоя.

## 🎛️ Команды CLI (Hardhat Ignition Commands)

Основные команды для управления процессом деплоя:

| Команда | Описание |
| :--- | :--- |
| `deploy` | Развернуть модуль. **Флаги:** `--reset`, `--verify`, `--strategy create2`. |
| `status <ID>` | Показать текущий статус деплоя. |
| `deployments` | Показать список всех ID деплоев. |
| `wipe <ID> <FutureID>` | **Сбросить состояние** конкретного плана (`Future`) в журнале (нужно после несовместимых изменений). |
| `verify <ID>` | **Верифицировать** контракты уже развернутого деплоя. |
| `visualize <path>` | Сгенерировать **HTML-граф** зависимостей модуля. |
| `transactions <ID>` | Показать все транзакции, связанные с деплоем. |

### Переменные Окружения (Env Vars)

* `HARDHAT_IGNITION_CONFIRM_DEPLOYMENT=false`: Отключает запрос подтверждения при деплое в live-сети.
* `HARDHAT_IGNITION_CONFIRM_RESET=false`: Отключает запрос подтверждения при использовании `--reset`. 

## 🎨 Визуализация и Отладка

  * **`npx hardhat ignition visualize ./path/to/Module.ts`**: Создает **HTML-отчет** (открывается в браузере), который показывает:
      * Сводку о контрактах и вызовах функций.
      * **Граф зависимостей** (`Future` Objects и Модулей) — помогает проверить, совпадает ли ваш план с фактическим порядком выполнения Ignition.

## 🛑 Обработка Ошибок и Изменений

### Ошибки Контрактов (Reverts)

Ignition сначала **симулирует** все транзакции.

1.  Если симуляция **не удалась**, выполнение останавливается. Просто **перезапустите** деплой.
2.  Если симуляция **удалась, но транзакция всё равно откатилась** (reverted) в сети, вам нужно **вручную сбросить** это действие, а затем перезапустить деплой.

### Сброс Ошибки (Wiping)

Если вы **изменили код** `Future` (контракта/вызова), который уже начал выполняться и попал в журнал (journal), вам нужно "стереть" старую запись:

```bash
npx hardhat ignition wipe <deploymentId> <futureId>
```

### Изменение Модуля (Resume)

  * Вы можете **добавить новые** контракты или вызовы в уже развёрнутый модуль.
  * При повторном запуске Ignition **продолжит с места остановки** и выполнит только новые части.
  * Для **полного сброса** и начала деплоя с нуля (игнорируя журнал): используйте флаг `--reset`.

<!-- end list -->

```bash
npx hardhat ignition deploy ... --reset
```

## 🧪 Использование Ignition в Тестах

Вы можете использовать `ignition.deploy` прямо в тестах, чтобы быстро настроить тестовую среду (`fixture`).

  * **Деплой в тестах:** Используйте `await connection.ignition.deploy(YourModule)`.
  * **Результат:** Метод возвращает **готовые экземпляры контрактов** (Viem Contract Instances или Ethers.js Contract Instances, в зависимости от плагина).
  * **Параметры:** Можете передать параметры прямо в функцию `deploy`:
    ```javascript
    await connection.ignition.deploy(Module, {
      parameters: { ModuleId: { paramName: 42 } }
    });
    ```
  * **Отправитель по умолчанию:** Можно изменить аккаунт, который будет отправлять все транзакции: `defaultSender: second.account.address`.

## 🔐 Верификация и Развертывание в Live-сетях

### Верификация Контрактов (Etherscan)

  * Верификация делает исходный код контракта **публичным** (на Etherscan), что критично для открытости.
  * **Требуется:** Ключ `apiKey` Etherscan, добавленный в конфиг Hardhat.
  * **Флаг `--verify`:** Добавьте его к команде деплоя, чтобы Ignition **автоматически верифицировал** контракты после успешного развертывания.

<!-- end list -->

```bash
npx hardhat ignition deploy ignition/modules/Apollo.ts --network sepolia --verify
```

### Детерминированный Деплой (Create2)

  * `create2` позволяет развернуть контракт на **заранее известном (детерминированном) адресе**, который будет одинаковым в разных сетях.
  * **Требуется:** Добавить **`salt`** (уникальную 32-байтовую строку) в конфигурацию.
  * **Флаг `--strategy create2`:** Используйте его при деплое.

<!-- end list -->

```bash
npx hardhat ignition deploy ... --strategy create2
```

## 🔄 Обновляемые Контракты (Proxies)

Ignition отлично подходит для деплоя **обновляемых (Upgradeable)** контрактов (например, TransparentUpgradeableProxy от OpenZeppelin).

1.  **Развертывание Proxy:**
      * Деплоите **Implementation V1** (логика контракта).
      * Деплоите **Proxy**, указывая V1 как его реализацию.
      * Ignition может считать адрес `ProxyAdmin` из **события** (`m.readEventArgument`).
2.  **Обновление:**
      * Деплоите **Implementation V2**.
      * Используете `m.call` для вызова функции **`upgradeAndCall`** у контракта `ProxyAdmin` (для смены логики и вызова функции инициализации V2).
3.  **Взаимодействие:**
      * Используете `m.contractAt("DemoV2", proxy)` — это позволяет вам работать с **новым ABI** через старый адрес прокси.

## 📜 Деплой через Hardhat Scripts

Некоторые операции (**условная логика, `async/await`, логирование**) **невозможны** внутри самого модуля Ignition. Используйте **Hardhat Scripts** для "обертывания" деплоя:

| Задача | Как сделать |
| :--- | :--- |
| **Деплой:** | `const { contract } = await connection.ignition.deploy(YourModule);` |
| **Логирование:** | `console.log(contract.address)` — можно получить адрес после деплоя. |
| **Async/API:** | Выполните `await` вызов **перед** `ignition.deploy`. Результат передайте как **параметр** в модуль. |
| **Условная логика:** | Используйте `if`/`else` в скрипте, чтобы решать, **вызывать ли** `ignition.deploy` вообще. |
